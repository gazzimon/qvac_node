Runbook de implementación bajo reloj

QVAC-Node reorientado al Pears Track: un CLI instalable con pear install pear://<key>, con actualizaciones OTA P2P, que al instalarse entra a una red de inferencia viva. Bare + @qvac/bare-sdk + Hyperswarm + bare-http1.

Horizonte: 24h Track: 🍐 Pears (Tether) Pool: $1.500 USDt Juzgado: domingo 13:00 ARG
Principio rector

Lo que se decide una vez y no se vuelve a discutir

  1. pear install pear://<key> desde una máquina limpia es el criterio de juzgado #1, y se prueba en la Fase 0 — no al final. El jurado instala tu app como lo haría un usuario. Es una compuerta binaria: anda o no anda. Si el túnel de distribución no está probado a H+3, no hay submission y hay que decirlo en voz alta, no seguir programando features.
  2. El jurado nunca descarga un modelo. El gateway funciona con cero modelo y enruta a los nodos seedeados. serve usa un modelo ≤1B con descarga opt-in explícita. Wifi de venue más 2,5 GB en el momento del juicio es la forma más tonta de perder el track.
  3. El install es la demo. Instalar no es el preámbulo de la demo: es la demo. La máquina del jurado entra al topic Hyperswarm en vivo y ve tokens en streaming desde nodos reales en menos de 60 segundos.
  4. El process shape se elige con criterio y se justifica por escrito en el README. Es criterio de juzgado explícito, no una nota de implementación. Variante main (updater en worker thread): el OTA no puede bloquear el streaming de tokens.
Diferencias con el runbook anterior

Qué se retira, y por qué

El plan anterior optimizaba para un pitch de arquitectura P2P a 48h. El Pears Track puntúa otra cosa: install limpio, OTA funcionando, process shape adecuado y utilidad práctica. Varias piezas que eran “intocables” dejan de pagar, y varias que eran “detalle de packaging” pasan a ser el centro.

PiezaAntesAhora
Gateway ciego / cifrado E2E Invariante #1, “desde el primer commit” Sale del plan. Pears no lo puntúa. Se conserva la disciplina de interfaz (el gateway relaya el cuerpo, no lo inspecciona) porque es gratis, pero no se implementa criptografía.
WDK / recibos / liquidación Fase 4 completa Sale entero. Cero puntos en este track, y su compatibilidad con Bare no está verificada.
Distribución por npm “Parte del producto” Se invierte: el canal es pear install. La red distribuye su propio cliente por la red.
Runtime Node.js “En Fase 0/1 NO usamos Bare” Revertido. QVAC soporta Bare ≥1.24 oficialmente, con @qvac/bare-sdk dedicado. La premisa que justificaba evitarlo era falsa.
Fastify Gateway HTTP No corre bajo Bare. Va bare-http1 con SSE por chunked writes manuales. Es el único bloque no trivial de la migración.
Generación de JSON Schema schema:gen + test de comparación Se recorta. Era un lujo de presupuesto de 48h. Queda el zod y firma/verificación.
Dependencias

Camino crítico

Tres tareas bloquean todo lo demás, y la primera no es de producto. El orden invierte el instinto natural: se prueba primero cómo se entrega, después qué se entrega. Un binario trivial que instala y se actualiza vale más, a esta altura del reloj, que un nodo perfecto que nadie puede instalar.

1 · Túnel de distribución

pear touch → stage → seed → install desde una segunda máquina. Bloquea absolutamente todo.

2 · QVAC bajo Bare

@qvac/bare-sdk + addon @qvac/llm-llamacpp registrado explícitamente. En Bare nada se auto-registra.

3 · Gateway sin fastify

bare-http1 con SSE manual. Es la reescritura, no un port.

Demo / submission

Seeder 24/7, ensayo de OTA en vivo, video de respaldo, README con la justificación del process shape.

Ejecución

Fases con bloques horarios

FASE 0

El túnel de distribución, primero

H+0 → H+3

Probar el pipeline completo de entrega con una app trivial, antes de escribir una línea de lógica de negocio. Todo lo demás del hackathon se apoya en que esto funcione.

Distribución

  • Clonar hello-pear-bare, variante main (pear-runtime en worker thread).
  • pear touch y pegar el link en el campo upgrade del package.json. Si queda el placeholder, arranca con INVALID_URL.
  • pear stage <link> y pear seed <link>.
  • pear install pear://<key> desde una segunda máquina limpia.

Prueba de OTA

  • Un bin qvac-node que solo imprime --help y una versión.
  • Cambiar el string de versión, re-stagear, y ver la copia ya instalada actualizarse sola.
  • Anotar el flag --no-updates para desarrollo.
Definition of done

Una segunda máquina instala desde el link y recibe una actualización OTA sin intervención manual.

Riesgo principal

Es la compuerta binaria del track. Si a H+3 no anda, se escala y se replantea el track — no se sigue de largo esperando que se acomode.

FASE 1

QVAC corriendo adentro de Bare

H+3 → H+7

Inferencia local real desde adentro de la app Pear. Sigue sin haber red ni gateway: solo un prompt que responde.

Nodo

  • qvac doctor como preflight.
  • Instalar @qvac/bare-sdk y el addon @qvac/llm-llamacpp — el SDK no trae addons por defecto.
  • Proveer el global process y registrar los plugins explícitamente.
  • Modelo ≤1B respondiendo un prompt dentro del worker.

Tamaño del bundle

  • qvac bundle sdk para un worker bundle tree-shakeado si el peso molesta al instalar.
  • Medir cuánto pesa el install real: es lo que el jurado va a esperar descargando.
Definition of done

La app instalada por pear install responde un prompt con inferencia 100% local.

Riesgo principal

El registro de addons. En Bare nada se auto-registra y los errores son poco descriptivos. Presupuestar tiempo de pelea acá, no darlo por trivial.

FASE 2

Nodo, manifiesto firmado y swarm

H+7 → H+11

El nodo se anuncia en un topic fijo con un manifiesto firmado que otros pueden verificar. Acá es donde la app deja de ser un CLI y pasa a ser una red.

Manifiesto

  • Portar manifest-v0.json a zod 4 (ya es dependencia de @qvac/bare-sdk, no hay conflicto de versión).
  • signManifest / verifyManifest: Ed25519 sobre JCS (RFC 8785), con test de caso negativo.
  • Sin generación de JSON Schema ni test de comparación — recortado.

Swarm

  • hyperswarm ya viene con el SDK. Topic fijo, hardcodeado.
  • El nodo publica su manifiesto firmado al conectarse con un par.
  • Un manifiesto que no verifica se descarta antes de leer pricing.
Definition of done

Dos nodos en máquinas distintas se descubren en el topic e intercambian manifiestos verificados.

Riesgo principal

Irse por la madriguera del protocolo. El manifiesto acá es medio, no fin: Pears no puntúa elegancia de esquema. Timeboxear duro.

FASE 3

Gateway sobre bare-http1

H+11 → H+15

La reescritura que reemplaza a fastify. Endpoint compatible con OpenAI, streaming de punta a punta, y decisión de routing loggeada.

Gateway

  • POST /v1/chat/completions sobre bare-http1.
  • SSE a mano: chunked writes manuales, sin helpers de fastify.
  • Elige entre los pares del topic filtrando por modelId y por capabilities.streaming.
  • Log de routing en JSON-Lines append-only: qué candidatos había, cuál eligió, por qué.

Cero modelo

  • El gateway arranca sin ningún modelo descargado. Es la pieza que hace viable el demo del jurado.
  • Si no hay pares, mensaje claro — nunca un cuelgue silencioso.
Definition of done

Un curl con "stream": true devuelve tokens desde otro nodo, y el log muestra por qué se eligió ese.

Riesgo principal

Subestimar el SSE manual. El framing de data: y el flush por chunk son exactamente donde se pierden dos horas.

FASE 4

El install es la demo

H+15 → H+18

Convertir el criterio de juzgado #1 en el momento más fuerte del pitch: una máquina virgen entra a la red en menos de un minuto.

Recorrido del jurado

  • pear install pear://<key> en una máquina que nunca vio el proyecto.
  • qvac-node gateway → tokens en streaming desde tus nodos seedeados.
  • Cronometrarlo. Objetivo: bajo 60 segundos, sin descarga de modelo.
  • qvac-node serve como el camino opcional para aportar cómputo.

Infraestructura

  • Seeder dedicado 24/7, no la laptop de la demo.
  • 2 nodos de demo encendidos y anunciándose en el topic.
  • Probar el recorrido completo desde una red distinta a la del venue.
Definition of done

Instalación cronometrada desde máquina limpia hasta primer token en menos de 60 segundos, tres veces seguidas.

Riesgo principal

Que el seeder viva en una laptop que alguien cierra para ir a dormir. Va en una máquina que no se toca.

FASE 5

OTA en vivo y endurecimiento

H+18 → H+21

El criterio de juzgado #2, ensayado hasta que sea aburrido.

Demo de OTA

  • Bumpear versión y pear stage en vivo; el nodo corriendo toma el update en escena.
  • Que el cambio sea visible: un banner, un color, un comando nuevo. Nada de diffs invisibles.
  • Ensayarlo al menos tres veces. Es 60 segundos de demo y pega justo en el rubric.

Endurecimiento

  • Matar un nodo a mitad de stream y ver qué hace el gateway. Arreglarlo o documentarlo honestamente.
  • Flujo completo tres veces consecutivas sin tocar código.
Definition of done

El update OTA se propaga a una instancia corriendo, en vivo, con un cambio visible a simple vista.

Riesgo principal

Ensayar el OTA por primera vez sobre el escenario. La propagación tiene latencia variable: hay que saber cuánto tarda antes de contarlo.

FASE 6

Submission y pitch

H+21 → H+24

Los requisitos de entrega son entregables duros, no buenas intenciones. Se cierran acá con tiempo, no a las corridas.

Entregables

  • Repo público con README y el pear:// key bien visible arriba de todo.
  • Justificación escrita del process shape elegido — criterio de juzgado explícito.
  • Links directos al código de integración con Pear y con QVAC.
  • Instrucciones de setup verificadas desde install limpio.

Cierre

  • Video de respaldo del recorrido completo, reproducido una vez en la laptop de la demo.
  • 2–3 slides: el install como demo, el diagrama de la red, el OTA.
  • Ensayo cronometrado.
Definition of done

El video existe y se probó; el README permite a un desconocido instalar y usar la red sin preguntarte nada.

Riesgo principal

Ninguno técnico. Acá el riesgo es llegar sin dormir y con el pitch sin cronometrar.

Si el reloj aprieta

Tabla de recorte de emergencia

El orden está invertido respecto del runbook anterior. Lo que antes era el corazón del pitch (directorio P2P, gateway ciego) ahora es recortable; lo que antes parecía packaging ahora es intocable.

OrdenSe cortaImpacto
1 Manifiesto firmado con JCS → lista de pares hardcodeada con verificación mínima. Pears no puntúa el protocolo. Bajo
2 Routing por precio y latencia → round-robin entre pares vivos. El log de decisión se conserva igual: es barato y se ve bien. Bajo
3 Tres nodos → dos. Sigue mostrando selección entre candidatos. Bajo
4 Inferencia local en la máquina instalada → el install trae solo el gateway y enruta a los nodos seedeados. Achica el install y sigue siendo una demo completa. Medio
5 OTA en vivo → no se corta. Es el criterio de juzgado #2. Si no llega a estar ensayado, se muestra grabado, pero tiene que existir. Muy alto
6 pear install limpio → no se corta nunca. Sin esto no hay submission: el track dice explícitamente que un repo local no califica. Terminal
