Implementation runbook against the clock

QVAC-Node reoriented to the Pears Track: an installable CLI with pear install pear://<key>, with P2P OTA updates, that on install joins a live inference network. Bare + @qvac/bare-sdk + Hyperswarm + bare-http1.

Horizon: 24h Track: 🍐 Pears (Tether) Pool: $1,500 USDt Judging: Sunday 13:00 ARG
Guiding principle

What gets decided once and isn't revisited

  1. pear install pear://<key> from a clean machine is judging criterion #1, and it gets tested in Phase 0 — not at the end. The jury installs your app the way a user would. It's a binary gate: it works or it doesn't. If the distribution tunnel isn't tested by H+3, there is no submission, and that has to be said out loud, not papered over by continuing to build features.
  2. The jury never downloads a model. The gateway works with zero models and routes to seeded nodes. serve uses a ≤1B model with explicit opt-in download. Venue wifi plus 2.5 GB at judging time is the dumbest way to lose the track.
  3. The install is the demo. Installing isn't the preamble to the demo: it is the demo. The jury's machine joins the live Hyperswarm topic and sees streaming tokens from real nodes in under 60 seconds.
  4. The process shape is chosen deliberately and justified in writing in the README. It's an explicit judging criterion, not an implementation footnote. main variant (updater on a worker thread): the OTA update can't block token streaming.
Differences from the previous runbook

What's cut, and why

The previous plan optimized for a 48h P2P architecture pitch. The Pears Track scores something else: clean install, working OTA, the right process shape, and practical utility. Several pieces that were “untouchable” stop paying off, and several that were “packaging detail” become the center of the plan.

PieceBeforeNow
Blind gateway / E2E encryption Invariant #1, “from the first commit” Dropped from the plan. Pears doesn't score it. The interface discipline stays (the gateway relays the body, doesn't inspect it) because it's free, but no cryptography gets implemented.
WDK / receipts / settlement Full Phase 4 Dropped entirely. Zero points in this track, and its Bare compatibility isn't verified.
Distribution via npm “Part of the product” Inverted: the channel is pear install. The network distributes its own client over the network.
Node.js runtime “In Phase 0/1 we do NOT use Bare” Reversed. QVAC officially supports Bare ≥1.24, with a dedicated @qvac/bare-sdk. The premise that justified avoiding it was false.
Fastify HTTP gateway Doesn't run under Bare. Goes with bare-http1 and SSE via manual chunked writes. It's the only non-trivial block in the migration.
JSON Schema generation schema:gen + comparison test Trimmed. It was a luxury of the 48h budget. Zod plus signing/verification stay.
Dependencies

Critical path

Three tasks block everything else, and the first one isn't product work. The order inverts the natural instinct: test how it's delivered first, then what's delivered. A trivial binary that installs and updates is worth more, at this point in the clock, than a perfect node nobody can install.

1 · Distribution tunnel

pear touch → stage → seed → install from a second machine. Blocks absolutely everything.

2 · QVAC under Bare

@qvac/bare-sdk + @qvac/llm-llamacpp addon registered explicitly. In Bare, nothing self-registers.

3 · Gateway without fastify

bare-http1 with manual SSE. It's a rewrite, not a port.

Demo / submission

Seeder running 24/7, live OTA rehearsal, backup video, README with the process shape justification.

Execution

Phases with time blocks

PHASE 0

The distribution tunnel, first

H+0 → H+3

Test the full delivery pipeline with a trivial app, before writing a single line of business logic. Everything else in the hackathon depends on this working.

Distribution

  • Clone hello-pear-bare, main variant (pear-runtime on a worker thread).
  • pear touch and paste the link into the upgrade field of the package.json. If the placeholder is left in, it starts with INVALID_URL.
  • pear stage <link> and pear seed <link>.
  • pear install pear://<key> from a second, clean machine.

OTA test

  • A qvac-node bin that only prints --help and a version.
  • Change the version string, re-stage, and watch the already installed copy update itself.
  • Note the --no-updates flag for development.
Definition of done

A second machine installs from the link and receives an OTA update with no manual intervention.

Main risk

This is the track's binary gate. If it doesn't work by H+3, escalate and rethink the track — don't keep going and hope it sorts itself out.

PHASE 1

QVAC running inside Bare

H+3 → H+7

Real local inference from inside the Pear app. Still no network or gateway: just a prompt that gets answered.

Node

  • qvac doctor as preflight.
  • Install @qvac/bare-sdk and the @qvac/llm-llamacpp addon — the SDK doesn't ship addons by default.
  • Provide the global process and register the plugins explicitly.
  • ≤1B model answering a prompt inside the worker.

Bundle size

  • qvac bundle sdk for a tree-shaken worker bundle if the size hurts install time.
  • Measure how heavy the real install is: that's what the jury will be waiting to download.
Definition of done

The app installed via pear install answers a prompt with 100% local inference.

Main risk

Addon registration. In Bare nothing self-registers and errors aren't very descriptive. Budget fight time here, don't treat it as trivial.

PHASE 2

Node, signed manifest, and swarm

H+7 → H+11

The node announces itself on a fixed topic with a signed manifest that others can verify. This is where the app stops being a CLI and becomes a network.

Manifest

  • Port manifest-v0.json to zod 4 (already a dependency of @qvac/bare-sdk, no version conflict).
  • signManifest / verifyManifest: Ed25519 over JCS (RFC 8785), with a negative-case test.
  • No JSON Schema generation or comparison test — cut.

Swarm

  • hyperswarm already ships with the SDK. Fixed topic, hardcoded.
  • The node publishes its signed manifest when connecting with a peer.
  • A manifest that fails verification is discarded before reading pricing.
Definition of done

Two nodes on different machines discover each other on the topic and exchange verified manifests.

Main risk

Going down the protocol rabbit hole. The manifest here is a means, not an end: Pears doesn't score schema elegance. Timebox this hard.

PHASE 3

Gateway on bare-http1

H+11 → H+15

The rewrite that replaces fastify. OpenAI-compatible endpoint, end-to-end streaming, and a logged routing decision.

Gateway

  • POST /v1/chat/completions over bare-http1.
  • SSE by hand: manual chunked writes, no fastify helpers.
  • Chooses among the topic's peers, filtering by modelId and by capabilities.streaming.
  • Routing log in append-only JSON-Lines: what candidates existed, which one it picked, why.

Zero model

  • The gateway starts with no model downloaded. This is the piece that makes the jury demo viable.
  • If there are no peers, a clear message — never a silent hang.
Definition of done

A curl with "stream": true returns tokens from another node, and the log shows why that one was picked.

Main risk

Underestimating manual SSE. The data: framing and per-chunk flush are exactly where two hours get lost.

PHASE 4

The install is the demo

H+15 → H+18

Turn judging criterion #1 into the strongest moment of the pitch: a clean machine joins the network in under a minute.

Jury walkthrough

  • pear install pear://<key> on a machine that's never seen the project.
  • qvac-node gateway → streaming tokens from your seeded nodes.
  • Time it. Target: under 60 seconds, no model download.
  • qvac-node serve as the optional path for contributing compute.

Infrastructure

  • Dedicated seeder, 24/7, not the demo laptop.
  • 2 demo nodes up and announcing themselves on the topic.
  • Test the full walkthrough from a network different from the venue's.
Definition of done

Timed install from a clean machine to first token in under 60 seconds, three times in a row.

Main risk

The seeder living on a laptop someone closes to go to sleep. It goes on a machine nobody touches.

PHASE 5

Live OTA and hardening

H+18 → H+21

Judging criterion #2, rehearsed until it's boring.

OTA demo

  • Bump the version and pear stage live; the running node picks up the update on stage.
  • Make the change visible: a banner, a color, a new command. No invisible diffs.
  • Rehearse it at least three times. It's 60 seconds of demo and lands right on the rubric.

Hardening

  • Kill a node mid-stream and see what the gateway does. Fix it or document it honestly.
  • Full flow, three times in a row, without touching code.
Definition of done

The OTA update propagates to a running instance, live, with a change visible at a glance.

Main risk

Rehearsing the OTA for the first time on stage. Propagation has variable latency: you need to know how long it takes before talking about it.

PHASE 6

Submission and pitch

H+21 → H+24

Submission requirements are hard deliverables, not good intentions. Close them out here with time to spare, not at a run.

Deliverables

  • Public repo with README and the pear:// key clearly visible at the top.
  • Written justification of the chosen process shape — explicit judging criterion.
  • Direct links to the Pear and QVAC integration code.
  • Setup instructions verified from a clean install.

Wrap-up

  • Backup video of the full walkthrough, played once on the demo laptop.
  • 2–3 slides: the install as demo, the network diagram, the OTA.
  • Timed rehearsal.
Definition of done

The video exists and has been tested; the README lets a stranger install and use the network without asking you anything.

Main risk

None technical. The risk here is showing up sleep-deprived with an untimed pitch.

If the clock runs short

Emergency cut table

The order is inverted from the previous runbook. What used to be the heart of the pitch (P2P directory, blind gateway) is now cuttable; what used to look like packaging is now untouchable.

OrderCutImpact
1 JCS-signed manifest → hardcoded peer list with minimal verification. Pears doesn't score the protocol. Low
2 Price- and latency-based routing → round-robin among live peers. The decision log stays the same either way: it's cheap and it looks good. Low
3 Three nodes → two. Still shows selection among candidates. Low
4 Local inference on the installed machine → the install ships only the gateway and routes to seeded nodes. Shrinks the install and it's still a complete demo. Medium
5 Live OTA → not cuttable. It's judging criterion #2. If it isn't rehearsed in time, show it recorded, but it has to exist. Very high
6 Clean pear install → never cuttable. Without this there's no submission: the track explicitly says a local repo doesn't qualify. Terminal
